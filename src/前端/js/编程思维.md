# 编程思维

编程思维是解决问题的方式，不同的编程范式提供了不同的组织代码和抽象问题的思路。常见的有面向对象编程（OOP）、函数式编程（FP）和函数响应式编程（FRP）。

## 1. OOP 面向对象编程

OOP（Object-Oriented Programming）以**对象**为核心，将数据和行为封装在一起，通过对象之间的协作来完成任务。

### 核心概念

- 封装：把数据和对数据的操作封装在对象内部，对外只暴露必要接口
- 继承：子类复用父类的属性和方法，实现代码复用
- 多态：同一接口在不同对象上有不同的实现，调用时根据实际类型执行
- 抽象：提取共性形成类或接口，隐藏具体实现细节

```js
class Animal {
  constructor(name) {
    this.name = name;
  }

  makeSound() {
    console.log('某种声音');
  }
}

class Dog extends Animal {
  // 多态：重写父类方法
  makeSound() {
    console.log('wang');
  }
}

class Cat extends Animal {
  makeSound() {
    console.log('miao');
  }
}

const animals = [new Dog('旺财'), new Cat('咪咪')];
animals.forEach((animal) => animal.makeSound());
```

### 适用场景与优缺点

- 适合业务实体清晰、状态和行为紧密关联的场景，如组件、领域模型
- 优点：封装性好，易于理解现实世界模型，代码复用方便
- 缺点：继承层级过深会导致耦合严重，`this` 指向容易出错，状态共享带来副作用

## 2. FP 函数式编程

FP（Functional Programming）以**函数**为核心，把计算过程看作函数的组合，强调无副作用和不可变数据。

### 核心概念

- 纯函数：相同输入永远得到相同输出，且不产生副作用
- 不可变数据：不直接修改原数据，而是返回新的数据
- 函数是一等公民：函数可以赋值给变量、作为参数传递、作为返回值
- 高阶函数：接收函数作为参数或返回函数的函数
- 函数组合：把多个小函数组合成更复杂的函数
- 柯里化：把多参数函数转换成一系列单参数函数

```js
// 纯函数：不修改外部状态
const add = (a, b) => a + b;

// 不可变：返回新数组，而不是修改原数组
const push = (arr, item) => [...arr, item];

// 高阶函数
const compose =
  (...fns) =>
  (x) =>
    fns.reduceRight((acc, fn) => fn(acc), x);

const toUpper = (str) => str.toUpperCase();
const exclaim = (str) => `${str}!`;

const shout = compose(exclaim, toUpper);
shout('hello'); // 'HELLO!'

// 柯里化
const curryAdd = (a) => (b) => a + b;
curryAdd(1)(2); // 3

// 数组方法也是典型的高阶函数
[1, 2, 3].map((n) => n * 2).filter((n) => n > 2);
```

### 适用场景与优缺点

- 适合数据处理、状态转换、工具函数等场景，在前端中与 `React`、`Redux` 结合紧密
- 优点：可预测、易测试、易组合，天然适合并发和缓存
- 缺点：过度使用会降低可读性，频繁创建新对象有性能开销，学习和调试曲线较陡

## 3. FRP 函数响应式编程

FRP（Functional Reactive Programming）是**响应式编程**与**函数式编程**的结合，把随时间变化的数据抽象成**数据流（Stream）**，通过订阅流来响应数据的变化。

### 核心概念

- 数据流：把事件、用户输入、网络请求等看作随时间产生值的数据流
- 响应式：数据变化会自动传播到依赖它的地方，无需手动触发更新
- 操作符：对流进行映射、过滤、合并、防抖等操作，风格类似函数式编程
- 声明式：描述"数据是什么"以及"如何转换"，而不是命令式地手动处理每一步

### 与响应式编程的区别

- 响应式编程强调的是"数据变化自动传播"这一思想，如 `Vue` 的响应式系统
- FRP 更强调用函数式的方式组合和转换数据流，典型代表是 `RxJS`、`Most.js`

```js
// RxJS 示例：监听输入框，做防抖后输出
import { fromEvent } from 'rxjs';
import { map, debounceTime, distinctUntilChanged } from 'rxjs/operators';

const input = document.querySelector('#search');

fromEvent(input, 'input')
  .pipe(
    map((event) => event.target.value),
    debounceTime(300),
    distinctUntilChanged(),
  )
  .subscribe((keyword) => {
    console.log('搜索：', keyword);
  });
```

前端框架中的响应式也体现了这一思想：

```js
// Vue3 的响应式：数据变化自动触发依赖更新
import { ref, watchEffect } from 'vue';

const count = ref(0);

watchEffect(() => {
  console.log('count 变为：', count.value);
});

count.value++; // 自动打印
```

### 适用场景与优缺点

- 适合处理复杂的异步事件流，如搜索联想、拖拽、WebSocket、轮询
- 优点：声明式处理异步和事件，逻辑清晰，易于组合和取消
- 缺点：概念抽象、上手成本高，简单场景使用反而增加复杂度

## 4. AOP 面向切面编程

AOP（Aspect-Oriented Programming）面向切面编程，用于把**横切关注点**从核心业务逻辑中分离出来。像日志、鉴权、缓存、埋点、异常处理这类逻辑，会散落在多个模块中，与业务代码交织在一起，AOP 就是把这些重复且与业务无关的逻辑抽取成"切面"，在不修改原代码的情况下统一织入。

### 核心概念

- 横切关注点：跨越多个模块的通用逻辑，如日志、权限校验、性能监控
- 切面（Aspect）：横切关注点的模块化封装
- 连接点（Join Point）：程序执行过程中可以被织入的点，如函数调用前后
- 切点（Pointcut）：通过规则匹配需要织入的连接点
- 通知（Advice）：在连接点上执行的具体动作，如前置、后置、环绕通知
- 织入（Weaving）：把切面应用到目标对象的过程

### JavaScript 中的实现

`JavaScript` 没有原生的 AOP 语法，通常通过高阶函数包装、装饰器或 `Proxy` 来实现。

```js
// 通过高阶函数实现环绕通知：在目标函数前后织入逻辑
function withLogging(fn) {
  return function (...args) {
    console.log(`调用 ${fn.name}，参数：`, args);
    const start = performance.now();

    const result = fn.apply(this, args);

    console.log(`耗时 ${performance.now() - start}ms`);
    return result;
  };
}

function fetchData(id) {
  return { id, name: '张三' };
}

const wrappedFetch = withLogging(fetchData);
wrappedFetch(1);
```

使用装饰器可以更贴近 AOP 的写法（装饰器目前需要通过 `babel` 或 `tsc` 编译使用）：

```js
// 方法装饰器：为方法统一添加日志
function log(target, name, descriptor) {
  const original = descriptor.value;

  descriptor.value = function (...args) {
    console.log(`${name} 被调用`);
    return original.apply(this, args);
  };

  return descriptor;
}

class UserService {
  @log
  getUser(id) {
    return { id };
  }
}
```

使用 `Proxy` 可以对整个对象的访问进行拦截，实现通用的切面逻辑：

```js
const target = {
  get(id) {
    return { id };
  }
};

const proxy = new Proxy(target, {
  get(obj, prop) {
    const value = obj[prop];
    if (typeof value === 'function') {
      return (...args) => {
        console.log(`调用 ${prop}`);
        return value.apply(obj, args);
      };
    }
    return value;
  }
});

proxy.get(1);
```

### 适用场景与优缺点

- 适合日志、鉴权、缓存、埋点、错误处理、性能监控等与业务无关又需要统一处理的场景，在 `NestJS`、`Spring` 等框架中应用广泛
- 优点：分离关注点，业务代码更纯粹，通用逻辑集中管理、便于复用
- 缺点：织入过程隐蔽，调试时调用链不直观，切面过多会让代码可读性下降

## 5. IoC 控制反转与 DI 依赖注入

IoC（Inversion of Control）控制反转是一种设计原则，DI（Dependency Injection）依赖注入是它最常见的实现方式。二者常一起出现，核心都是**解耦**。

### 控制反转 IoC

传统写法中，一个对象需要使用依赖时，会自己在内部创建它，依赖的创建和生命周期都由自己控制。

```js
// 传统写法：内部自己 new，耦合严重
class UserService {
  constructor() {
    this.db = new MySQLDatabase();
  }

  getUser(id) {
    return this.db.query(id);
  }
}
```

控制反转就是把"创建依赖"的控制权从对象内部交出去，由外部的容器或框架来负责。对象的职责变纯粹，只关注自己的业务逻辑。

### 依赖注入 DI

依赖注入是 IoC 的具体落地方式：依赖不再由对象自己创建，而是在创建对象时由外部"注入"进来。

```js
// 依赖注入：依赖从构造函数传入
class UserService {
  constructor(db) {
    this.db = db;
  }

  getUser(id) {
    return this.db.query(id);
  }
}

// 由外部决定注入哪种实现
const userService = new UserService(new MySQLDatabase());
```

常见的注入方式：

- 构造函数注入：依赖通过构造函数参数传入，最常用，依赖清晰可见
- 属性注入：通过给属性或 setter 赋值传入，如 `this.db = db`
- 接口注入：依赖提供方实现统一接口，容器按接口注入

注入接口而非具体实现，还可以方便地替换实现，例如测试时注入一个 Mock：

```js
class MockDatabase {
  query(id) {
    return { id, name: '测试数据' };
  }
}

const service = new UserService(new MockDatabase());
```

### 简单容器实现

IoC 容器负责依赖的注册、实例化和自动装配。

```js
class Container {
  constructor() {
    this.registry = new Map();
  }

  // 注册依赖及其工厂函数
  register(name, factory) {
    this.registry.set(name, factory);
  }

  // 解析依赖，支持自动注入
  resolve(name) {
    const factory = this.registry.get(name);
    if (!factory) {
      throw new Error(`未注册的依赖：${name}`);
    }
    return factory(this);
  }
}

const container = new Container();

container.register('db', () => new MySQLDatabase());
container.register('userService', (c) => new UserService(c.resolve('db')));

const userService = container.resolve('userService');
```

在 `NestJS` 中，IoC 容器和依赖注入是框架内置能力，通过装饰器声明即可：

```ts
@Injectable()
class UserService {
  constructor(private readonly db: DatabaseService) {}

  getUser(id: string) {
    return this.db.query(id);
  }
}
```

### 适用场景与优缺点

- 适合模块较多、依赖关系复杂、需要方便替换实现或做单元测试的项目，`NestJS`、`Spring` 等框架均内置 IoC 容器
- 优点：降低耦合，便于替换实现和测试，依赖关系集中管理
- 缺点：引入了容器和额外概念，依赖不直观，排查问题需要理解容器装配过程

## 6. 编程范式对比

| 对比项   | OOP                         | FP                              | FRP                  | AOP                        | IoC / DI                  |
| -------- | --------------------------- | ------------------------------- | -------------------- | -------------------------- | ------------------------- |
| 核心     | 对象                        | 函数                            | 数据流               | 切面                       | 依赖的控制权              |
| 数据     | 可变，封装在对象内          | 不可变                          | 随时间变化的流       | 不关注数据本身             | 不关注数据本身            |
| 关注点   | 谁来做（对象协作）          | 做什么（函数组合）              | 数据如何随时间流动   | 横切逻辑如何织入           | 依赖由谁创建和提供        |
| 副作用   | 允许，依靠封装控制          | 尽量避免                        | 集中在订阅处处理     | 在连接点统一处理           | 集中在容器装配过程        |
| 典型代表 | `Java`、`C++`、`class 组件` | `Haskell`、`lodash/fp`、`Redux` | `RxJS`、`Vue` 响应式 | `NestJS`、装饰器、`Proxy`  | `NestJS`、`Spring`、`Angular` |

这些概念并非互斥，实际项目中常常结合使用：用 OOP 组织业务实体，用 FP 处理数据转换，用 FRP 处理异步数据流，用 AOP 统一处理日志、鉴权等横切逻辑，用 IoC / DI 管理对象之间的依赖关系。
